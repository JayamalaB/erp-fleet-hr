# ERP / Fleet Management / HR & Payroll — Reference Implementation

A MERN implementation of the core functionality described in the three assessment briefs
(`ERP_Accounting_Assessment_Task.pdf`, `Fleet_Management_Assessment_Task.pdf`,
`HR_Payroll_Assessment_Task.pdf`), built as one connected system: Fleet trips generate
driver bonuses that Payroll consumes exactly once, and all three modules stay decoupled
via an internal domain-event bus. The full architecture rationale, data model, worked
scenarios, and answers to every "critical engineering question" from the briefs are in
`Technical_Approach_Assessment.docx`; this README covers running the code that implements it.

## Structure

```
server/   Node.js + Express + MongoDB (Mongoose) API - all business logic and tests
client/   React (Vite) frontend - one screen per module
```

Inside `server/src/modules/` there are three independent modules (`accounting`, `fleet`,
`hr`), each with its own models, services, routes, and `eventHandlers.js`. They share a
`platform/` layer (auth, multi-tenant query scoping, the domain-event bus, audit logging)
but never import each other's models directly.

## Prerequisites

- Node.js 20+ and npm
- A MongoDB **replica set** (not a standalone instance) - the app uses multi-document
  ACID transactions throughout the posting/payroll logic, which standalone MongoDB
  doesn't support. Two ways to get one, in order of ease:
  1. **No install needed**: `npm run dev:mongo` inside `server/` spins up a disposable
     local replica set (via `mongodb-memory-server`) and prints a `MONGODB_URI` to use.
     Data is lost when you stop it - fine for local development and demos.
  2. **MongoDB Atlas** (free tier, M0) - a real, persistent replica set out of the box.
     This is also what production deployment uses (see below).

## Local development

```bash
# 1. Start a database (pick one)
cd server && npm run dev:mongo        # prints MONGODB_URI - copy it
# --- or use an Atlas connection string directly ---

# 2. Configure and start the API
cd server
cp .env.example .env                  # then paste your MONGODB_URI into .env
npm install
npm run dev                           # http://localhost:4000

# 3. Start the frontend (in a second terminal)
cd client
npm install
npm run dev                           # http://localhost:5173
```

Open `http://localhost:5173`, register a company, and walk through each module's tab.

## Tests

```bash
cd server
npm test
```

20 tests across three suites, each spinning up its own disposable in-memory replica set
(no external DB needed to run them):

- `tests/accounting.scenario.test.js` - the worked VAT/AR scenario, double-posting
  (including a real concurrent race), reversal-based cancellation, period locking,
  multi-company isolation.
- `tests/fleet.scenario.test.js` - the exact driver-reassignment/completed-trip
  integrity scenario from the brief, inactive-vehicle rejection, per-km pricing.
- `tests/hr.scenario.test.js` - the worked net-salary scenario, duplicate trip-bonus
  prevention through the real event bus, payroll locking, full termination/EOS math.

## Deployment (MongoDB Atlas + Render + Vercel)

All three have a free tier sufficient for this project.

1. **Database - MongoDB Atlas**
   - Create a free M0 cluster at [mongodb.com/atlas](https://www.mongodb.com/atlas) (an
     Atlas cluster is already a replica set, so transactions work out of the box).
   - Create a database user and allow network access from anywhere (`0.0.0.0/0`) or
     Render's IPs.
   - Copy the connection string - this becomes `MONGODB_URI`.

2. **API - Render**
   - Push this repo to GitHub.
   - In Render, "New +" → "Blueprint", point it at the repo - it will read
     `render.yaml` (at the repo root) and provision the service automatically.
   - Set `MONGODB_URI` (from step 1) and `CORS_ORIGIN` (your Vercel URL, from step 3) in
     the Render dashboard's environment variables - these two are intentionally left
     unset in `render.yaml` since they're per-deployment secrets/URLs.
   - `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are auto-generated by the Blueprint.

3. **Frontend - Vercel**
   - Import the repo in Vercel, set the project root to `client/`.
   - Set the environment variable `VITE_API_URL` to your Render service's URL.
   - Deploy - `client/vercel.json` handles the build output and SPA routing.

4. Update the Render service's `CORS_ORIGIN` to the final Vercel URL and redeploy the API
   so the browser's CORS check passes.

## What's intentionally out of scope

Per the assessments' own instruction to focus on core functionality rather than a full
production system: no email/SMS delivery for document-expiry alerts (logged to console
instead), no file storage integration for documents (a `fileRef` field is stored but
nothing uploads to it), and the "unapplied receipts" sub-ledger for partially-allocated
payments is called out in code comments as a known simplification rather than built out.
Each is a straightforward extension of the existing service-layer pattern, not a design
gap.
